# [ADR-0001] Uso de Kong API Gateway para la migración de OLDMAN a YOUNGMAN

* **Estado:** Propuesto
* **Decisores:** [Arquitectura de TI, líder técnico y responsable del producto]
* **Stakeholders:** [Desarrollo, Operaciones, Infraestructura, Seguridad, QA y Negocio]
* **Fecha:** 2026-11-10

---

## 1. Contexto y Declaración del Problema

El plan de modernización contempla la migración progresiva del sistema legado
**OLDMAN 5.0** hacia el nuevo sistema **YOUNGMAN 0.0.1**.

Durante esta migración se requiere mantener la máxima disponibilidad posible del
servicio. Las funcionalidades serán migradas gradualmente a YOUNGMAN, por lo que
ambos sistemas deberán coexistir temporalmente y recibir solicitudes durante el
periodo de transición.

Para habilitar esta convivencia se necesita un componente que permita enrutar
las solicitudes hacia el sistema responsable de cada funcionalidad. Las
funcionalidades que ya hayan sido migradas deberán ser atendidas por YOUNGMAN,
mientras que las funcionalidades pendientes continuarán siendo procesadas por
OLDMAN.

También se requiere contar con un mecanismo de contingencia que permita
redirigir una funcionalidad migrada hacia el flujo legado cuando se presente un
incidente crítico en YOUNGMAN.

Las principales fuerzas y limitantes consideradas son:

* Mantener la máxima disponibilidad posible durante la migración.
* Evitar una sustitución completa de tipo *big bang*.
* Habilitar la convivencia temporal de OLDMAN y YOUNGMAN.
* Migrar y liberar funcionalidades de forma incremental.
* Reducir el impacto de incidentes en las nuevas funcionalidades.
* Permitir la reversión controlada hacia el flujo legado.
* Centralizar las reglas de enrutamiento.
* Aplicar controles de seguridad, autenticación y autorización.
* Mantener trazabilidad sobre el sistema que atiende cada solicitud.
* Evitar que el mecanismo de enrutamiento se convierta en un punto único de
  fallo.
* Controlar el costo operativo de mantener ambos sistemas activos.

---

## 2. Opciones Consideradas

* **Opción 1:** Implementar el enrutamiento directamente en los clientes.
* **Opción 2:** Utilizar Kong API Gateway como punto central de enrutamiento.
* **Opción 3:** Realizar un cambio completo de OLDMAN a YOUNGMAN.
* **Opción 4:** Mantener todo el tráfico en OLDMAN hasta concluir la migración.

---

## 3. Decisión Tomada

Decidimos seleccionar la **Opción 2: utilizar Kong API Gateway como punto
central de enrutamiento**, porque permite dirigir las solicitudes hacia OLDMAN
o YOUNGMAN mediante reglas centralizadas, sin trasladar esta responsabilidad a
los sistemas consumidores.

Kong API Gateway se utilizará para enrutar hacia YOUNGMAN las funcionalidades
que hayan sido migradas y validadas. Las funcionalidades pendientes de
migración continuarán siendo atendidas por OLDMAN.

En caso de que una funcionalidad migrada presente un incidente crítico en
YOUNGMAN, se podrá aplicar una regla de contingencia para redirigir las
solicitudes hacia el flujo legado en OLDMAN, siempre que ambos sistemas
mantengan compatibilidad funcional y contractual para dicha operación.

El enrutamiento no deberá depender de cambios manuales no controlados. Las
configuraciones deberán versionarse, probarse y promoverse mediante los
mecanismos establecidos de despliegue.

La habilitación de cada funcionalidad migrada deberá contemplar:

1. Identificación de las rutas y operaciones que serán migradas.
2. Confirmación de la compatibilidad de los contratos de entrada y salida.
3. Configuración de los servicios y rutas correspondientes en Kong.
4. Aplicación de los controles de autenticación y autorización requeridos.
5. Ejecución de pruebas funcionales, de integración, carga y resiliencia.
6. Liberación gradual de la funcionalidad hacia YOUNGMAN.
7. Monitoreo técnico y funcional posterior a la liberación.
8. Validación del procedimiento de reversión hacia OLDMAN.
9. Retiro de la ruta legado cuando YOUNGMAN alcance la estabilidad acordada.

### Razones Principales de la Elección

* Centraliza las reglas de enrutamiento entre OLDMAN y YOUNGMAN.
* Permite liberar las funcionalidades migradas de manera incremental.
* Reduce la necesidad de modificar los sistemas consumidores.
* Facilita la reversión controlada hacia el flujo legado.
* Permite aplicar políticas transversales de seguridad y control de tráfico.
* Proporciona un punto común para observabilidad y trazabilidad.
* Se alinea con el patrón Strangler Fig para la modernización gradual.
* Ofrece un balance adecuado entre continuidad operativa, esfuerzo y riesgo.

## 4. Análisis Comparativo de Opciones

### Opción 1: Enrutamiento implementado directamente en los clientes

* **Ventajas:**
  * No requiere incorporar una nueva capa de infraestructura.
  * Cada cliente puede controlar directamente el sistema que consume.
  * Puede resultar sencillo cuando existe un solo consumidor.

* **Desventajas:**
  * Duplica las reglas de enrutamiento en múltiples aplicaciones.
  * Requiere modificar y desplegar cada cliente.
  * Incrementa el acoplamiento de los consumidores con OLDMAN y YOUNGMAN.
  * Dificulta ejecutar una reversión rápida y coordinada.
  * Puede generar comportamientos inconsistentes entre consumidores.
  * Reduce la visibilidad centralizada del tráfico.

### Opción 2: Kong API Gateway como punto central de enrutamiento

* **Ventajas:**
  * Centraliza las rutas y las políticas de tráfico.
  * Oculta a los consumidores la coexistencia de ambos sistemas.
  * Permite migrar funcionalidades de manera gradual.
  * Facilita el redireccionamiento controlado hacia el flujo legado.
  * Permite aplicar autenticación, autorización y límites de consumo.
  * Proporciona métricas y registros centralizados.
  * Reduce el acoplamiento entre los consumidores y los sistemas internos.
  * Permite administrar las configuraciones mediante automatización.

* **Desventajas:**
  * Agrega una capa adicional a la arquitectura.
  * Requiere infraestructura de alta disponibilidad para Kong.
  * Puede convertirse en un punto crítico si no se configura correctamente.
  * Introduce latencia adicional en las solicitudes.
  * Requiere monitoreo, mantenimiento y soporte especializado.
  * Las reglas incorrectas podrían dirigir tráfico al sistema equivocado.
  * El retorno al flujo legado depende de que OLDMAN mantenga compatibilidad.

### Opción 3: Cambio completo de OLDMAN a YOUNGMAN

* **Ventajas:**
  * Reduce el tiempo de coexistencia de ambos sistemas.
  * Simplifica el estado final de la arquitectura.
  * Evita mantener reglas temporales de enrutamiento.
  * Permite retirar OLDMAN en una sola liberación.

* **Desventajas:**
  * Incrementa el riesgo de indisponibilidad.
  * Concentra todos los cambios en una única liberación.
  * Dificulta la reversión parcial de las funcionalidades.
  * Retrasa la entrega de valor hasta completar toda la migración.
  * Puede exponer brechas funcionales o de infraestructura en producción.

### Opción 4: Mantener el tráfico en OLDMAN hasta concluir la migración

* **Ventajas:**
  * Conserva temporalmente el flujo operativo actual.
  * Evita la convivencia de tráfico productivo entre ambos sistemas.
  * Reduce la complejidad inicial del enrutamiento.

* **Desventajas:**
  * Impide liberar valor de manera incremental.
  * Retrasa la validación de YOUNGMAN con tráfico real controlado.
  * Mantiene la dependencia total del sistema legado.
  * Acumula los riesgos de integración hasta el final de la migración.
  * Puede derivar en una migración de tipo *big bang*.

## 5. Consecuencias e Impacto

### Positivas (Beneficios)

* OLDMAN y YOUNGMAN podrán coexistir durante la migración.
* Las funcionalidades podrán migrarse y habilitarse progresivamente.
* Los consumidores utilizarán un punto de entrada estable.
* Se centralizarán las reglas de enrutamiento.
* Se reducirá el impacto de incidentes en las funcionalidades nuevas.
* Se podrá retornar temporalmente al flujo legado cuando sea compatible.
* Se obtendrán métricas centralizadas para ambos sistemas.
* Será posible incorporar controles comunes de seguridad y tráfico.
* Se reducirá el riesgo de una migración completa de tipo *big bang*.
* Se facilitará el retiro gradual de las funcionalidades de OLDMAN.

### Negativas / Riesgos (Compromisos)

* Kong se convertirá en un componente crítico de la solución.
* La plataforma deberá desplegarse con alta disponibilidad.
* Se agregará latencia al procesamiento de las solicitudes.
* Será necesario administrar y versionar las reglas de enrutamiento.
* Una configuración incorrecta podría afectar ambos sistemas.
* Existirá un costo adicional de infraestructura, operación y monitoreo.
* Los equipos deberán contar con conocimientos para operar Kong.
* Mantener OLDMAN y YOUNGMAN activos incrementará temporalmente la complejidad.
* La reversión podría no ser posible si los contratos o los datos divergen.
* Los cambios de escritura podrían generar inconsistencias entre los sistemas.

### Medidas de Mitigación

* Desplegar Kong API Gateway con múltiples instancias.
* Evitar puntos únicos de fallo en la infraestructura y sus dependencias.
* Configurar verificaciones de salud para OLDMAN y YOUNGMAN.
* Administrar la configuración de Kong como código.
* Versionar y revisar las rutas antes de promoverlas.
* Automatizar los despliegues y evitar cambios manuales en producción.
* Ejecutar pruebas automáticas de rutas y políticas.
* Implementar métricas, registros, trazas y alertas.
* Configurar tiempos de espera y límites de tráfico apropiados.
* Documentar y probar el procedimiento de reversión.
* Definir una única fuente de verdad para los datos compartidos.
* Evitar reintentos automáticos en operaciones no idempotentes.
* Auditar los cambios de configuración y los accesos administrativos.
* Restringir la administración de Kong mediante controles de acceso.
* Establecer una fecha objetivo para retirar las rutas de OLDMAN.

### Criterios de Éxito

La decisión se considerará exitosa cuando:

* Kong opere con el nivel de disponibilidad acordado.
* Las rutas dirijan correctamente cada funcionalidad al sistema responsable.
* Las funcionalidades migradas operen de forma estable en YOUNGMAN.
* Las reglas de contingencia puedan activarse dentro del tiempo acordado.
* La reversión hacia OLDMAN no requiera cambios en los consumidores.
* Los contratos se mantengan compatibles durante la coexistencia.
* Las métricas permitan identificar qué sistema atiende cada solicitud.
* Los errores y tiempos de respuesta permanezcan dentro de los umbrales
  definidos.
* Las rutas de OLDMAN puedan retirarse progresivamente.
* Exista un plan aprobado para retirar definitivamente OLDMAN 5.0.
